1. КОНТЕКСТ ПРОЕКТА
================================================================================
1.1. Что за сервер
GachiCraft — RPG-сервер Minecraft с сильным сюжетом. Игроки — «воины
Последнего Легиона»: обычные люди с особой сывороткой, защищающие Землю от
инопланетного вторжения. На сервере несколько миров: главный спавн (город),
мир ресурсов, рейды, данжи и т.д. Ключевой мир — «мир войны» (war world):
карта порядка 1000×1000 блоков, где постоянно спавнятся враждебные мобы.

1.2. Что такое «private mobs» (личные мобы)
Отдельный плагин PrivateMobsX (пишется тем же заказчиком, исходники будут
доступны разработчику) спавнит мобов ЛИЧНО для одного игрока: другие игроки
этих мобов не видят и не сталкиваются с ними (используется перехват пакетов,
ProtocolLib). Это важно: каждый игрок сражается со своими мобами, но по
сюжету они «общие».
Iron Frontiers НЕ спавнит мобов сам. Он решает, КОГДА, ГДЕ и КАКИХ мобов
спавнить конкретному игроку, и просит PrivateMobsX сделать это через API
(раздел 18.1). Ему же нужна информация об убийствах (события PrivateMobsX).

1.3. Что такое Iron Frontiers
Плагин «захвата территорий враждебных мобов». Мир войны разбит на СЕКТОРА
(произвольные фигуры на плоскости XZ, без ограничения по высоте). Игроки
совместно убивают мобов в секторе; если суммарная скорость убийств
(kills per minute, kpm) в секторе достигает порога — сектор «захватывается»
игроками: меняются биом и часть блоков, мобы ненадолго перестают спавниться,
включается защита на время (SAFE). Затем, чтобы удержать сектор (HELD), нужно
поддерживать kpm не ниже порога удержания. Если kpm падает — запускается
обратный отсчёт, после которого сектор возвращается врагам (ENEMY), а все
изменения откатываются. Захваченный сектор можно «укрепить» — построить
форпост (здание из блоков), собрав общими усилиями ресурсы; форпост даёт
бонусы (дольше защита и т.д.).
Это ГЛАВНЫЙ плагин сервера: вокруг него будут строиться другие механики,
поэтому он обязан быть (а) максимально оптимизированным, (б) расширяемым,
(в) снабжённым собственным API.

1.4. Принципиальная идея геймдизайна (для понимания, зачем так)
Секторы НАМЕРЕННО постоянно переходят от игроков к мобам и обратно — это
создаёт причину заходить на сервер. Если никого нет онлайн, сектора могут
терять (настраивается). Игроки должны координироваться. Не добавляйте
«облегчений», не описанных в документе.

2. ГЛОССАРИЙ
================================================================================
Сектор (sector)      — зона мира войны: замкнутая фигура на плоскости XZ с
                       границами только вдоль осей X и Z. Высота не учитывается.
sector_id            — уникальное имя сектора (ключ в sectors.yml). Только
                       латиница, цифры, «_» и «-». Без пробелов.
display_name         — отображаемое имя сектора (с цветовыми кодами).
kpm                  — kills per minute: сумма «весов» убийств за последние 60 с.
kpm_capture          — kpm, достаточный для захвата.
kpm_held             — kpm, достаточный для удержания (раньше называлось
                       «retention»; везде используется ТОЛЬКО «held»).
Состояния сектора    — ENEMY, SAFE, HELD, DESTRUCTION.
Кластер (cluster)    — группа мобов (1–10), спавнится одновременно в формации.
Точка спавна/слот    — запись в sectors.<id>.mobs: кластер + координаты якоря.
Якорь (anchor)       — координаты x,y,z точки спавна кластера.
Сессия (player,sector)— состояние спавна для пары «игрок × сектор».
Форпост (stronghold) — здание в секторе, строится по чертежу из ресурсов.
Чертёж (blueprint)   — описание здания: «внутренняя координата → блок».
Внутренние координаты— система координат чертежа; (0,0,0) = центр (center).
Журнал замен         — бинарный файл со списком позиций блоков, которые
                       заменяются при захвате сектора (раздел 12).
Лидер                — сервер, принимающий решения при многосерверности.
Холостой старт       — первые startup_safe_seconds после запуска плагина.

Оригинальные названия из первых версий → итоговые (используйте ИТОГОВЫЕ):
  retention → held;   safe-time → safe_time;   destruction-time →
  destruction_time;   NPC → npc;   NPC_coord → npc_coord;   /ironfrontier
  sector new → /if sectors create.

3. ПРАВИЛА РАБОТЫ, РЕПОЗИТОРИЙ, ОТЧЁТНОСТЬ, КАЧЕСТВО

3.1. Репозиторий (GitHub)  [ОБЯЗАТЕЛЬНО]
  - main — всегда собирается и запускается. Работа — в ветках feature/<этап>-<тема>,
    слияние через Pull Request. Коммиты — осмысленные (Conventional Commits:
    feat:, fix:, refactor:, docs:, test:).
  - В репозитории должны лежать: исходники, pom.xml, этот документ
    (docs/PLAN.txt), примеры всех конфигов с комментариями (src/main/resources).

3.2. Письменная отчётность  [ОБЯЗАТЕЛЬНО]
Заказчик не читает код ежедневно. Поэтому после КАЖДОГО значимого изменения
(PR) разработчик обновляет текстовые файлы в репозитории (НЕ в коде):
  docs/STATUS.md       — таблица «возможность → статус (не начато / в работе /
                         готово / проверено) → как проверить вручную». Заказчик
                         по этому файлу проверяет, что уже должно работать.
  docs/CHANGELOG.md    — что добавлено/изменено/исправлено, по датам и версиям.
  docs/QUESTIONS.md    — открытые вопросы к заказчику (с вашим выбранным
                         безопасным вариантом по умолчанию).
  docs/decisions/NNN-название.md — записи о [РЕШЕНИЯХ РАЗРАБОТЧИКА] и о любых
                         отклонениях от этого документа (с причиной).
  docs/TESTING.md      — ручные сценарии проверки по этапам (шаги и ожидание).
Шаблон записи см. в разделе 24.1. Конец каждого этапа = PR + обновлённые файлы
+ краткая сводка «что работает, что нет, как проверить».

3.3. Качество кода  [ОБЯЗАТЕЛЬНО]
  - Java 21. Никаких статических синглтонов «где попало»: зависимости
    передаются через конструкторы (простая ручная DI, без фреймворков).
  - Чистая логика (геометрия, окно kpm, автомат состояний, формации, матчинг
    предметов, кодек журнала) НЕ должна зависеть от Bukkit — чтобы покрываться
    юнит-тестами (JUnit 5). Bukkit-обвязка — тонкий слой.
  - Код расширяем: внешние системы и хранилище — за интерфейсами (раздел 5),
    поведение настраивается конфигом, магические числа запрещены.
  - Комментарии/Javadoc на публичные классы API и на нетривиальные алгоритмы.
  - Логи: уровни INFO (жизненный цикл), WARNING (ошибки конфига, не фатальные),
    SEVERE (фатальное). Подробный лог — только при debug: true.

3.4. Производительность  [ОБЯЗАТЕЛЬНО]
Правила для кода, работающего во время игры (не на этапе создания секторов):
  - Главный поток: никакого блокирующего ввода-вывода (БД, Redis, файлы,
    сеть). Всё это — в отдельных пулах, результат возвращается на главный поток.
  - Обработка убийства — O(1), без аллокаций в горячем пути.
  - Никаких BukkitRunnable «на каждый таймер». Все таймеры (сотни штук) —
    в ОДНОМ центральном планировщике (очередь с приоритетом по времени или
    «колесо таймеров»), который тикает одной задачей Bukkit.
  - Массовые операции с миром (смена блоков/биомов, постройка) — только по
    бюджету времени на тик (раздел 12.5).
  - Целевой бюджет всего плагина в простое: < 0,5 мс/тик в среднем при 100
    секторах и 100 игроках (проверять через Spark). Фиксируйте замеры в
    docs/STATUS.md.
  - Этап СОЗДАНИЯ секторов — режим разработки: там допустима любая нагрузка
    (в т.ч. тяжёлое сканирование мира).

3.5. Ориентиры по времени
Не указаны намеренно: порядок и приёмка важнее скорости. Каждый этап
заканчивается приёмкой заказчиком по docs/STATUS.md.

4. ТЕХНИЧЕСКИЙ СТЕК, ЗАВИСИМОСТИ, СТРУКТУРА ПРОЕКТА

4.1. Платформа  [ОБЯЗАТЕЛЬНО]
  - Сервер: Purpur 1.20.6 (форк Paper). Java 21+. Сборщик: Maven (3.9+).
  - Компилировать против Paper API 1.20.6 (io.papermc.paper:paper-api,
    1.20.6-R0.1-SNAPSHOT, scope provided). Не использовать NMS/CraftBukkit
    без крайней необходимости; если понадобится — вынести в отдельный класс
    за интерфейсом и пометить в docs/decisions/.
  - Главный класс: com.gachicraft.ironfrontiers.IronFrontiers
  - Адвентюр-API (Component, MiniMessage) — встроен в Paper.

4.2. Структура Maven (multi-module)  [ОБЯЗАТЕЛЬНО]
  ironfrontiers-parent (pom)
   ├─ ironfrontiers-api   — только интерфейсы, события, DTO публичного API
   │                         (пакет com.gachicraft.ironfrontiers.api).
   │                         Без зависимости от реализации. Публикуется как
   │                         артефакт, чтобы другие плагины сервера
   │                         компилировались против него.
   └─ ironfrontiers-plugin — реализация, плагин (shade-jar).
  Версионирование API — semver; в api-модуле аннотировать @ApiStatus.

5. АРХИТЕКТУРА
================================================================================
5.1. Слои
  Конфиги → Модель (Sector, ClusterDef, Blueprint) → Сервисы (SectorService,
  SpawnDirector, TransformService, StrongholdService, MenuService) →
  Адаптеры (PrivateMobsBridge, CitizensBridge, …) → Хранилище.
  События Bukkit и команды — только «входы» в сервисы.

5.2. Центральные интерфейсы (заложить ДЛЯ БУДУЩЕЙ мультисерверности с первого
дня, хотя реализуется она в этапе 6)  [ОБЯЗАТЕЛЬНО]
  StateStore      — чтение/запись глобального состояния: состояния секторов,
                    форпостов, прогресс пожертвований, статистика игроков.
                    Реализация этапа 2: JdbcStateStore (MySQL, async).
  KpmSource       — источник суммарного kpm по сектору. Реализация этапа 2:
                    LocalKpmSource. Этап 6: ClusterKpmSource (суммирует kpm
                    с разных серверов).
  Authority       — «кто принимает решения о смене состояний». Реализация
                    этапа 2: AlwaysLeader (единственный сервер всегда лидер).
                    Этап 6: RedisLeaderElection.
  StateBroadcaster— уведомление остальных серверов о смене состояния.
                    Этап 2: NoopBroadcaster.
  PlayerCountSource— число игроков онлайн «в кластере» (для freeze_when_empty).
  Вся логика смены состояний (раздел 10) должна обращаться ТОЛЬКО к этим
  интерфейсам, а не к конкретным реализациям. Тогда этап 6 не потребует
  переписывания ядра.

5.3. Принцип «желаемое состояние ↔ применённое состояние» (reconcile)
[ОБЯЗАТЕЛЬНО] Состояние сектора в БД (SAFE/HELD/DESTRUCTION/ENEMY) — это
ЖЕЛАЕМОЕ состояние. Физическое состояние мира (блоки, биомы, форпост, NPC)
— ПРИМЕНЁННОЕ состояние, оно хранится локально на сервере (маркеры в чанках,
локальные файлы, раздел 12 и 13). Сервис reconcile сравнивает их и приводит
мир к желаемому состоянию: при старте сервера, при смене состояния, при
загрузке чанка. Операция должна быть ИДЕМПОТЕНТНОЙ и продолжаемой после
падения сервера. Этот принцип одновременно решает: рестарты, краши, прерывание
смены сектора, подключение нового сервера (этап 6).

5.4. Потоки
  Главный поток: все обращения к Bukkit API (мир, сущности, инвентари).
  Async-пулы (3 отдельных, именованные потоки): (1) БД; (2) файловый ввод-вывод
  и сканирование ChunkSnapshot; (3) Redis (этап 6).
  Правило: результат из async → в главный поток через планировщик Bukkit.
  Общие структуры между потоками — неизменяемые снимки (immutable snapshot)
  или ConcurrentHashMap; плейсхолдеры читают ТОЛЬКО снимки из памяти.

5.4.1. Центральный планировщик таймеров
  Один тикер (раз в 1 тик либо раз в 20 тиков — по типу задачи). Хранит
  таймеры сектора и спавна в очереди с приоритетом. API: schedule(key, delay),
  cancel(key), freeze/resume по группе. Время таймеров — «оставшиеся секунды»,
  а не абсолютные метки (см. 10.5).

5.5. Обработка ошибок конфигов
  Ошибка в конфиге одного сектора/кластера/чертежа НЕ должна отключать плагин:
  этот объект помечается невалидным, пишется WARNING с путём к ключу, остальные
  работают. Фатальны только: недоступная БД при старте (раздел 17.4),
  отсутствие PrivateMobsX.

5.6. Расширяемость (на будущее)  [ОБЯЗАТЕЛЬНО]
  - Кастомные события Bukkit для всех значимых переходов (раздел 19).
  - Реестры (SectorRegistry, ItemMatcherRegistry, BlockApplier и т.д.) с
    возможностью регистрации новых реализаций.
  - Версия схемы БД и версия формата журнала — с миграциями.
  - Не «зашивать» названия миров, состояния и числа в код.

  - coords: ≥1 вершины; каждая "x,z" — целые; к загруженному контуру

    числа (можно дробные), respawn — секунды ≥ 0 (откат точки, раздел 11).

    внутри как целые десятые. Предупреждение, если kpm_held > kpm_capture.

    requirements; requirements_repair опционален (если нет — починка
    бесплатна и мгновенно доступна). center должен лежать внутри сектора
    (проверка вхождения всей постройки НЕ требуется).
  - Остальные поля-таймеры: сначала значение сектора, иначе sector_defaults.
Запись нового сектора из игры (раздел 8) ДОПИСЫВАЕТСЯ в конец sectors.yml
текстово (без перезаписи файла, чтобы не потерять комментарии админа).
Удаление сектора — текстовое удаление его блока (по отступам). Для этого

================================================================================
7. ГЕОМЕТРИЯ СЕКТОРОВ
================================================================================
7.1. Модель
Сектор — множество «столбцов» (клеток) на плоскости XZ. Клетка = один блок
(x, z). Высота НЕ учитывается: клетка (213, 321) занимает всю высоту мира.
Сектор задаётся замкнутым контуром из вершин (x,z) с рёбрами только вдоль
осей. Территория сектора = клетки на рёбрах (граница ВКЛЮЧЕНА) + все клетки
внутри контура. Вершины — центры клеток (целые координаты блоков).
Особые случаи: 1 вершина = сектор из одной клетки; 2+ вершин, лежащих на
одной прямой (монотонно) = «линейный сектор» (клетки отрезка).

7.2. Алгоритм растеризации (построчное заполнение)  [ОБЯЗАТЕЛЬНО]
Вход: список вершин V0..Vn-1 (целые x,z); рёбра Vi→Vi+1 и замыкающее
Vn-1→V0, все осевые. Выход: для каждой строки z — набор непересекающихся
отрезков по x.
  1. Для каждого ребра определить: вертикальное (x=const, меняется z) или
     горизонтальное (z=const, меняется x).
  2. Клетки границы: для каждого ребра включить ВСЕ клетки от одного конца до
     другого включительно.
  3. Внутренность: для каждой строки z от z_min до z_max взять вертикальные
     рёбра с диапазоном [za, zb) — нижний конец ВКЛЮЧЁН, верхний ИСКЛЮЧЁН
     (za<zb): если za ≤ z < zb, ребро пересекает строку в точке x. Отсортировать
     найденные x, объединить в пары (x1,x2),(x3,x4)… (правило чётности) и
     заполнить отрезки [x1..x2].
  4. Объединить внутренность и границу по каждой строке в слитые отрезки.
Полуоткрытое правило нужно, чтобы вершины не считались дважды.
КОНТРОЛЬНЫЙ ПРИМЕР (обязательный юнит-тест): вершины (0,0),(3,0),(3,2),(5,2),
(5,-4),(0,-4). Ожидаемый результат — 36 клеток: строки z=-4…0 → x∈[0..5]
(6 клеток × 5 строк = 30); строки z=1 и z=2 → x∈[3..5] (3 × 2 = 6).
Другие тесты: одна клетка (1 вершина); отрезок; прямоугольник; Г-образная,
Т-образная и «зубчатая» фигуры; фигура с вогнутым «карманом».

7.3. Правила валидности контура  [ОБЯЗАТЕЛЬНО]
(Используются и при загрузке sectors.yml, и при выделении в игре.)
  G1. Все точки в одном мире.
  G2. Каждое ребро (включая замыкающее) строго вдоль оси: у соседних вершин
      равен либо x, либо z (не оба: совпадающие подряд точки запрещены).
  G3. Соседние рёбра не могут «разворачиваться на 180°» (наезжать друг на
      друга). Две подряд коллинеарные рёбра в ОДНУ сторону допустимы (лишняя
      вершина; при сохранении нормализовать — удалить).
  G4. Несмежные рёбра не имеют общих клеток (никакого пересечения, касания,
      наложения). Смежные рёбра делят только общую вершину.
  G5. Результирующая территория не пересекается с другими секторами.
  G6. Координаты в пределах границы мира (WorldBorder).
Особый случай: ≤2 вершин либо все вершины коллинеарны и монотонны — это
«линейный/точечный сектор», правила G3–G4 к нему не применяются.
«Бубликов» (дыр) не бывает: всё внутри внешнего контура — сектор (контур не
самопересекается по G4).

7.4. Индексы после загрузки  [ОБЯЗАТЕЛЬНО]
  - Прямоугольники: объединить одинаковые отрезки соседних строк в
    непересекающиеся прямоугольники (z0..z1, x0..x1). Используются для
    расстояний и обхода территории.
  - ChunkIndex: Map<chunkKey(long) → ChunkCoverage>. ChunkCoverage —
    список пар (индекс сектора, маска). Если чанк целиком внутри сектора —
    флаг FULL, иначе маска 16×16 (4 long). Запрос «в каком секторе точка (x,z)»
    — O(1) без аллокаций.
  - Для каждого сектора: bounding box, площадь (число клеток), список якорей
    mobs, нулевая точка (первая вершина).
Мир порядка 1000×1000 → ~4000 чанков: память пренебрежимо мала.

7.5. Запросы геометрии (интерфейс SectorGeometry, чистая Java)
  sectorAt(worldId, x, z) → индекс|-1
  sectorsNear(worldId, x, z, radius) → индексы секторов, у которых есть клетка
        в окне чанков вокруг точки (быстрый отсев), затем точное расстояние
        до прямоугольников
  distanceToSector(index, x, z) → минимальное расстояние до ближайшей клетки
  cells(index) → итерация по клеткам/прямоугольникам; area(index)

7.6. Высота поверхности (Bukkit-часть)
SurfaceResolver.top(world, x, z, refY): сверху вниз от min(maxY, refY+8) найти
первый блок с непустой коллизионной формой (не воздух, не жидкость, не
проходимый). Результат — y блока + максимум Y его коллизионной формы (плита
0.5, ступень, полный блок 1.0). Используется для частиц (8.5) и для
безопасной точки tp (+1 к высоте, проверка 2 блоков воздуха). Кэшировать на
время показа. Не более 300 новых столбцов в тик.

================================================================================
8. ИНСТРУМЕНТ ВЫДЕЛЕНИЯ СЕКТОРА (/if sectors create)
================================================================================
8.1. Общий сценарий
  1. Админ вводит /if sectors create <название>. Название — ^[A-Za-z0-9_-]+$,
     уникально. Иначе — ошибка из messages.yml.
  2. Админу выдаётся «палка выделения»: материал selection.tool_material
     (STICK), название из messages.yml, ЭФФЕКТ ЗАЧАРОВАНИЯ визуально
     (ItemMeta#setEnchantmentGlintOverride(true), без реальных чар). Предмет
     помечается в PersistentDataContainer (ключ ironfrontiers:selection_tool,
     значение = имя создаваемого сектора) — распознавание только по PDC.
  3. ЛКМ палкой по блоку — ставит вершину (только основная рука; игнорировать
     дубли события; «защёлка» 150 мс).
  4. Shift+ПКМ (по блоку или в воздух) — отмена последней вершины.
  5. Завершение — ТОЛЬКО повторным ЛКМ по ПЕРВОЙ вершине (никаких команд
     finish; правки — потом в sectors.yml).
  6. Одна активная сессия на админа; при выходе/смене мира сессия
     сбрасывается (палка остаётся, но не работает — сообщение «сессия
     потеряна»). Палка должна быть уникальной: повторный create отменяет
     предыдущую сессию и заменяет палку.

8.2. Палка не ломает блоки  [ОБЯЗАТЕЛЬНО]
Отменять: BlockBreakEvent, BlockDamageEvent (в креативе ломание мгновенное),
PlayerInteractEvent (LEFT_CLICK_BLOCK) — все, где в основной руке палка с
PDC-меткой. Проверить вручную в креативе и выживании.

8.3. Правила добавления вершины (сообщения-ошибки — в messages.yml)
Клик по блоку B=(x,z) (y игнорируется, но запоминается как «подсказка высоты»
для tp/частиц):
  - Первая вершина — любая; мир сессии = мир блока.
  - Вершина другого мира → ошибка.
  - k-я вершина (k≥2), B ≠ V0: должна отличаться от предыдущей РОВНО по одной
    оси (G2). Иначе ошибка + ПОДСКАЗКА допустимых координат: «x={prev.x} (z
    любой) или z={prev.z} (x любой)». Автоматического «прилипания» к оси НЕ
    делать (может дезориентировать).
  - Должны выполняться G3–G4 для нового ребра (иначе ошибка с указанием
    причины).
  - Клик по V0 (первой вершине):
      · если вершин 1 → сектор из ОДНОЙ клетки (завершение);
      · если вершин ≥2 → попытка ЗАМКНУТЬ: замыкающее ребро (последняя→V0)
        должно быть осевым (иначе ошибка с подсказкой: «последняя точка должна
        иметь x={V0.x} или z={V0.z}») и удовлетворять G3–G4; для коллинеарных
        монотонных вершин — линейный сектор.
  - После успешного замыкания проверка G5 и G6.
8.4. Завершение  [ОБЯЗАТЕЛЬНО]
  1. Нормализовать вершины (убрать лишние коллинеарные).
  2. Дописать блок сектора в sectors.yml (текстово, 6.3) со значениями-
     заготовками: display_name '&6<название>', world, coords, пустые mobs: {}
     и закомментированные необязательные ключи.
  3. Зарегистрировать сектор в рантайме сразу (состояние ENEMY, строка в БД).
     Секторы без mobs/replaces допустимы (просто «пустые»).
  4. Закрыть сессию, убрать палку, сообщение об успехе.
8.5. Предпросмотр частицами (во время выделения и /if sectors show)
  - Линия рисуется НАД блоками, на ribbon_height_offset (0,1) выше верхней
    точки коллизии столбца (SurfaceResolver.top), а не внутри блока.
  - По каждому ребру идём клетка за клеткой; в клетке рисуем точки на высоте
    её столбца; между соседними клетками разной высоты дорисовываем
    ВЕРТИКАЛЬНЫЙ отрезок на их общей границе от меньшей высоты до большей —
    получается ступенчатая лента без разрывов.
  - Для незавершённого контура: нарисованные рёбра + «призрачное» последнее
    ребро от последней вершины до клетки, на которую смотрит админ (по желанию).
  - Тип частицы: DUST (цвет настраивается константами): рёбра — один цвет,
    первая вершина — другой, последняя — третий. Показ только самому админу
    (player.spawnParticle), только клетки в радиусе particle_view_radius,
    шаг particle_step.
  - Обновление раз в 5–10 тиков; в /if sectors show — до selection.
    show_duration_seconds секунд, потом автоматически прекращается.

================================================================================
9. СЧЁТЧИК kpm
================================================================================
9.1. Что считаем
kpm сектора = сумма «весов» убийств мобов ЭТОГО сектора ВСЕМИ игроками за
последние window_seconds (60). Моб принадлежит сектору по тегу if_sector,
который вы ставите при спавне (раздел 11, 18.1); место, где моб умер, роли не
играет. Убийство засчитывается, если убийца = владелец моба (PrivateMobsX
гарантирует; всё прочее — игнорировать). Вес записи кластера (weight, по
умолчанию 1.0) кладётся в тег if_weight в десятых долях (целое).

9.2. Структура (скользящее окно)  [ОБЯЗАТЕЛЬНО]
  KpmWindow: кольцевой буфер int[60] (бакет = 1 секунда, значения в десятых),
  бегущая сумма total, метка последней секунды. add(tenths, nowSec):
  «прокрутить» окно до nowSec (обнулить пропущенные бакеты, максимум 60), затем
  прибавить. sum(nowSec): прокрутить, вернуть total. Всё O(1), без аллокаций.
  Время — Bukkit-тики/System.nanoTime, не часы системы (устойчиво к
  переводу времени).
  Окно есть: на каждый сектор; на каждую пару (игрок, сектор) — лениво (создаётся
  при первом убийстве игрока в секторе, удаляется после
  kpm.player_idle_cleanup_seconds без убийств).

9.3. Снимки
Каждые kpm.update_interval_seconds (1..60) KpmTracker.tick() делает снимок:
  SectorKpmSnapshot {sectorId, kpm (double из десятых), time}. Снимки лежат в
  неизменяемой карте (AtomicReference). Автомат (раздел 10), плейсхолдеры (16)
  и публичный API читают ТОЛЬКО снимки. Параметр влияет на скорость реакции
  автомата и частоту записи в БД, а не на стоимость подсчёта (она ничтожна:
  бегущая сумма).
9.4. Эффективные пороги
  base_capture = override из БД (/if sectors set) ?? kpm_capture сектора ??
  sector_defaults.kpm_capture. То же для held.
  effective_held = base_held × (stronghold.kpm_held_multiplier, если форпост
  ACTIVE; иначе 1.0). Округление до десятых (HALF_UP). capture форпостом не
  меняется.
9.5. Игроки
  %if_player_kpm% — kpm игрока в секторе, где он СТОИТ (по позиции); вне
  сектора 0. %if_player_<имя>_kpm% — по указанному сектору. %if_player_kpm_sum%
  — сумма по всем окнам игрока.
9.6. Многосерверность (этап 6): KpmSource суммирует локальные бакеты со
  всех серверов (раздел 20.4). Игровой (персональный) kpm — только локальный.

================================================================================
10. СОСТОЯНИЯ СЕКТОРА И ТАЙМЕРЫ
================================================================================
10.1. Четыре состояния (названия утверждены)  [ОБЯЗАТЕЛЬНО]
  ENEMY       — сектор под контролем мобов. Мир в «вражеском» виде.
  SAFE        — только что захвачен игроками, защитный режим. Потерять нельзя
                (ничего не проверяется), kpm не важен.
  HELD        — удерживается, пока kpm ≥ held.
  DESTRUCTION — kpm упал ниже held: идёт обратный отсчёт до потери.
Сверх этого — ВНУТРЕННИЕ флаги (не отдельные публичные состояния):
  occupation_left_s — «оккупация»: после потери сектор нельзя отвоевать
  (внутри ENEMY); spawn_pause_left_s — пауза спавна после захвата;
  initializing — сектор в процессе первичной сверки мира (12.8).
10.2. Переменные сектора (хранятся в БД, раздел 17)
  state; state_left_s (SAFE и DESTRUCTION); occupation_left_s;
  destruction_saved_s и resume_window_left_s (для 10.4); version.
10.3. Тик автомата  [ОБЯЗАТЕЛЬНО] (каждые update_interval_seconds, dt=интервал;
выполняет ТОЛЬКО тот, кто Authority — лидер; в одиночном режиме всегда он)
  frozen = (холостой_старт_активен) ИЛИ (freeze_when_empty И игроков = 0)
  ENEMY:
    если occupation_left>0 → уменьшать на dt (если !frozen_by_empty);
    иначе если kpm ≥ capture_eff → захват(s).
  SAFE:
    если infinite_safe → ничего. Иначе если !frozen → state_left -= dt;
    при state_left ≤ 0 → если kpm ≥ held_eff то HELD, иначе начатьРазрушение().
  HELD:
    если !frozen И kpm < held_eff → начатьРазрушение().
  DESTRUCTION:
    если kpm ≥ held_eff → held_ok += dt, иначе held_ok = 0;
    если held_ok ≥ destruction_cancel_hold_seconds → вернутьВHELD();
    иначе если !frozen → state_left -= dt; при ≤0 → потеря(s).
  resume_window_left_s уменьшается на dt (если !frozen), когда >0; при 0
  сбросить destruction_saved_s.
Захват во время frozen разрешён (замораживаются только пути к потере).
10.4. Переходы
  захват(s): state=SAFE; state_left=safe_eff; held_ok=0; сбросить сохранённый
    остаток; spawn_pause_left=spawn_pause_after_capture_seconds; желаемая
    трансформация мира = PLAYER (раздел 12); NPC форпоста → в сектор (13.6);
    событие SectorCapturedEvent; сообщение игрокам. Окно kpm НЕ сбрасывается.
    safe_eff = (safe_time сектора ?? default); если форпост ACTIVE —
    × stronghold.safe_time_multiplier.
  начатьРазрушение(): state=DESTRUCTION; held_ok=0; state_left = если
    resume_window_left_s>0 и destruction_saved_s задан → destruction_saved_s,
    иначе destruction_eff. destruction_eff = (destruction_time ?? default);
    если форпост ACTIVE — × destruction_time_multiplier. Сообщение (с
    объединением, 10.9).
  вернутьВHELD(): state=HELD; destruction_saved_s=state_left_s;
    resume_window_left_s=destruction_resume_window_seconds. Сообщение.
    (Антидребезг: игрок не может обнулять таймер, «подпрыгивая» над порогом;
    kpm должен продержаться ≥ held заданное число секунд, а при повторном
    падении в окне возобновления таймер ПРОДОЛЖАЕТСЯ с остатка.)
  потеря(s): state=ENEMY; occupation_left=occupation_time (сектор ??
    default); желаемая трансформация = ENEMY; форпост (если есть и не
    NOT_BUILT) → BROKEN и запуск анимации разрушения (13.5); NPC на парковку;
    событие SectorLostEvent; сообщение (с объединением).
  Если сектор потерян, пока форпост строится/чинится: сборку прервать после
  текущего слоя и сразу выполнить разрушение (правило 13.5).
10.5. Таймеры как «остаток секунд»  [ОБЯЗАТЕЛЬНО]
  state_left_s, occupation_left_s и т.п. хранятся как ОСТАТОК, а не как
  абсолютное время. Простой выключенного сервера не «съедает» таймеры. Запись
  в БД: при каждом изменении состояния — сразу (асинхронно); остатки — каждые
  state_persist_interval_seconds (по умолчанию 10) и при остановке плагина.
  При падении теряется максимум этот интервал.
10.6. «Холостой старт» (startup_safe_seconds=300)  [ОБЯЗАТЕЛЬНО]
  Только при ВКЛЮЧЕНИИ плагина (не при /if reload!) запускается общий счётчик.
  Пока он идёт: frozen=true для путей к потере (SAFE/HELD/DESTRUCTION не
  теряются, таймеры стоят), а захват ENEMY игроками возможен. Это защита от
  потерь из-за того, что игроки ещё не успели зайти после рестарта.
  В многосерверном режиме: холостой старт выдаёт лидер только если кластер
  «холодно стартовал» (лидера не было дольше cold_start_gap_seconds).
10.7. freeze_when_empty  [ОБЯЗАТЕЛЬНО]
  false (по умолчанию): пустой онлайн ничего не меняет — сектора теряются.
  true: если игроков = 0, таймеры SAFE/DESTRUCTION/occupation замораживаются,
  новые потери не начинаются; как только онлайн ≥1 — всё продолжается.
  «Игроков» = все игроки сервера (не только в мире войны). В многосерверном
  режиме игроки считаются по ВСЕМУ кластеру (сумма по серверам из heartbeat):
  состояния глобальны, поэтому, если хоть на одном сервере есть игроки,
  сектор может быть потерян.
10.8. infinite_safe  [ОБЯЗАТЕЛЬНО]
  У сектора с infinite_safe: true при запуске плагина состояние принудительно
  SAFE (записать в БД), трансформация мира применена (PLAYER). kpm не
  проверяется, состояния не меняются. Спавн мобов, форпост и NPC работают.
  %if_sector_time% = infinite_time_text. Если админ убрал флаг и сделал
  /if reload — сектор остаётся SAFE с полным safe_eff (отсчёт начинается).
10.9. Сообщения (объединение)
  Сообщения о начале разрушения и о потере собираются в окне
  messages.batch_window_seconds: если за окно произошло ≥2 события одного вида —
  отправить ОДНО сообщение: «Над секторами AA24 и BB74 теряется контроль.
  Осталось 5 минут» (список имён через «, » и « и »; время — по таймеру;
  если у секторов разное время — писать для каждого). Аудитория: все игроки
  онлайн в war_worlds на этом сервере.
10.10. /if sectors set <имя> capture|held <значение>
  Пишет override в БД (таблица if_sector_override), действует сразу; в
  sectors.yml НЕ пишется. /if sectors info показывает оба значения.
  Значение ≤1 знак после запятой, >0.
10.11. События и порядок
  Любой переход: (1) изменить состояние в памяти; (2) записать в БД (async);
  (3) вызвать событие Bukkit; (4) запустить reconcile мира (раздел 12) и
  сообщения; (5) уведомить кластер (этап 6).

================================================================================
11. СПАВН МОБОВ
================================================================================
11.1. Общая идея
Для каждой пары (игрок, сектор) ведётся СЕССИЯ СПАВНА. В ней — состояния
точек спавна и таймеры. Мобы личные (PrivateMobsX), поэтому состояния
принадлежат конкретному игроку. Цель — «бесконечная» цепочка кластеров с
задержками, вынуждающими игрока ходить между точками/секторами.

11.2. Состояния точки (слота) в сессии  [ОБЯЗАТЕЛЬНО]
  IDLE     — свободна, мобов нет.
  WAIT     — зарезервирована под ближайший цепочный таймер.
  ACTIVE   — кластер жив (мобы заспавнены).
  COOLDOWN — кластер убит; точка недоступна respawn секунд (поле respawn).
Состояние сессии: armed (триггер взведён), chainStarted, chainTimer (с
номером шага n и текущей задержкой), starved (нет подходящих точек).

11.3. Подходящая точка (eligible)
Точка может быть выбрана, если одновременно:
  - состояние IDLE (не WAIT/ACTIVE/COOLDOWN);
  - чанк якоря ЗАГРУЖЕН (никогда не загружать чанки принудительно);
  - расстояние игрока до якоря ≥ spawn.min_spawn_distance;
  - число ACTIVE-кластеров в этом секторе у этого игрока < max_alive_clusters_
    per_sector И число ACTIVE-кластеров этого игрока во всех секторах <
    max_alive_clusters_total;
  - у сектора нет паузы спавна (spawn_pause_left_s = 0);
  - игрок онлайн, находится в том же мире.
«Ближайшая» = минимальное расстояние от игрока до якоря среди подходящих.
11.4. Алгоритм  [ОБЯЗАТЕЛЬНО]
  A) ТРИГГЕР. Каждые spawn.check_interval_ticks (10) для каждого игрока в
     war_worlds: sectorsNear(радиус trigger_distance) → для каждой сессии
     (создаётся лениво, armed=true): если armed и есть IDLE-точка с якорем
     ближе trigger_distance (15) → спавн ближайшей подходящей точки (ACTIVE),
     armed=false.
  B) ПЕРВАЯ СМЕРТЬ. Первая смерть любого моба сектора в сессии (chainStarted=
     false) → chainStarted=true; выбрать ближайшую подходящую точку → WAIT;
     запустить цепочный таймер на first_kill_timer_seconds (30).
  C) ТАЙМЕР СРАБОТАЛ. Если ограничения (11.3) позволяют — WAIT→ACTIVE
     (спавн). Если не позволяют (достигнут лимит живых кластеров/пауза) —
     повторять попытку раз в секунду, пока не разрешится. Затем следующий
     шаг: выбрать новую WAIT-точку (ближайшую подходящую, если есть),
     запустить таймер с задержкой на chain_delay_step_seconds (30) БОЛЬШЕ
     предыдущей (30, 60, 90 …), не более chain_delay_max_seconds (300).
     Таймер «живёт своей жизнью» независимо от того, сколько мобов убивает
     игрок. Большие задержки — осознанный дизайн (игрок ходит между секторами).
  D) КЛАСТЕР УБИТ ЦЕЛИКОМ. Точка → COOLDOWN (respawn секунд, потом →IDLE);
     тут же спавнится ближайшая подходящая точка (если есть) — «после убийства
     кластера всегда сразу появляется другой». Кластер из 1 моба: B и D
     происходят одновременно (сначала B, потом D; WAIT-точка исключается из D).
  E) НЕТ ПОДХОДЯЩИХ ТОЧЕК (все ACTIVE/WAIT/COOLDOWN, либо в чанках нет
     загруженных). Выставить starved=true. Как только какая-то точка станет
     подходящей (конец COOLDOWN или загрузка чанка) И игрок онлайн И он ближе
     despawn_distance (200) к ближайшему якорю сектора — спавнить её сразу.
  F) ПАУЗА ПОСЛЕ ЗАХВАТА. spawn_pause_left_s>0 — новые спавны запрещены
     (таймеры продолжают идти, срабатывание откладывается, см. C), уже
     живые мобы не трогаются. Мобы спавнятся и в SAFE/HELD (сектор игроков):
     «мобы всё равно спавнятся, просто не могут ничего захватывать».
11.5. Кластеры не повторяются
Поскольку точка в WAIT/ACTIVE/COOLDOWN не подходит под выбор, один и тот же
кластер подряд не выпадет, если есть альтернатива. Порядок — по расстоянию,
а не случайный (ближайшие к игроку).
11.6. Деспавн  [ОБЯЗАТЕЛЬНО] (деспавном управляет Iron Frontiers; из
PrivateMobsX своя логика деспавна УДАЛЯЕТСЯ — раздел 18.1)
  Три триггера:
   1) Игрок вышел с сервера → деспавн ВСЕХ мобов по ВСЕМ секторам, сессии
      удаляются, таймеры сбрасываются.
   2) Игрок сменил мир (PlayerChangedWorldEvent), и новый мир ≠ мир сектора →
      то же для секторов старого мира.
   3) Игрок дальше spawn.despawn_distance (200) от БЛИЖАЙШЕГО ЯКОРЯ сектора
      (проверка каждые despawn_check_interval_ticks) → деспавн ТОЛЬКО этого
      сектора для этого игрока; сессия сбрасывается (armed=true, точки IDLE).
  Деспавн РАСТЯГИВАЕТСЯ на spawn.despawn_spread_ticks (5..10) тиков: равные
  порции (ceil(N/ticks) на тик). После деспавна все таймеры сессии отменены.
  При отключении плагина — деспавн всех немедленно. При старте плагина —
  «подметание» (удалить всех мобов, оставшихся от прошлой сессии, через API
  PrivateMobsX).
11.7. Спавн кластера (процедура)
  1. Взять ClusterDef; развернуть записи в список мобов (amount шт.), перемешать.
  2. Рассчитать формацию (11.8) вокруг якоря; повернуть случайно на угол
     θ∈[0,2π); добавить небольшой шум (spawn.formation.jitter).
  3. Для каждой позиции найти «землю» (11.9). Не нашлась — пропустить моба
     (debug-лог). Если не заспавнился ни один — точка → IDLE и подавить
     повтор на 5 секунд.
  4. Уровень: для MYTHICMOBS вычислить (6.4), для VANILLA игнорировать.
  5. Для каждого моба вызвать PrivateMobsX API spawn(...) с тегами: if_sector,
     if_slot, if_cluster, if_entry, if_weight (десятые). Выставить yaw
     случайным (мобы смотрят в разные стороны).
  6. Слот → ACTIVE, запомнить дескрипторы (для подсчёта живых).
11.8. Формации (расстояние d = max(spawn.formation.spacing, 1.5 × ширина
самого широкого моба))  [ОБЯЗАТЕЛЬНО]
  n=1: центр.
  n=2: линия: точки (−d/2, 0) и (+d/2, 0).
  n=3: правильный треугольник, радиус описанной окружности R=d/√3, углы
       90°, 210°, 330°.
  n=4: квадрат со стороной d: (±d/2, ±d/2).
  n=5: «звезда» — вершины правильного пятиугольника, R = d / (2·sin 36°)
       (≈ d/1.1756), углы 90°+72°·k.
  n=6: прямоугольник 2×3: x∈{−d, 0, +d}, z∈{−d/2, +d/2}.
  n=7…10: случайные точки в круге радиусом R_max = d·√n·0,9 методом «метания
       дротиков» (Poisson-disc): мин. расстояние между точками d, до 30 попыток
       на точку; запасной вариант — центр + кольцо по окружности.
  Затем поворот на θ и jitter (для n≤6 jitter уменьшить вдвое, чтобы форма
  оставалась узнаваемой). Один и тот же формат для всех кластеров. Сумма
  amount ≤ 10 (валидация конфига).
11.9. Поиск «земли» для позиции (x,z)
  Начиная с y_якоря, перебирать смещения 0,+1,−1,+2,−2,… до ±
  ground_search_range: подходящий «feet y»: блок (y−1) с коллизией, блоки y и
  y+1 проходимы и не жидкость. Первое совпадение — позиция. Нет — моб
  пропускается.
11.10. Учёт убийств и kpm
  При смерти моба (событие PrivateMobsX) с тегом if_sector: (1) обновить
  состояние точки/сессии; (2) KpmTracker.recordKill(sector, игрок, вес);
  (3) пути B/D из 11.4. Все операции — O(1) на главном потоке.
11.11. Производительность и защита
  - Проверка триггера: только игроки в war_worlds, раз в 10 тиков, отбор
    секторов через ChunkIndex (а не перебор всех).
  - Лимит живых кластеров (два параметра, 11.3) — главная защита от
    лавинообразного спавна.
  - Все таймеры сессий — в центральном планировщике (5.4.1).
  - Память сессий очищается при деспавне/выходе игрока.11.12. Что я (автор документа) исправил в логике заказчика (для понимания)
  - Триггер привязан к якорю кластера, а не к границе сектора (иначе в
    больших секторах мобы появлялись бы далеко от игрока).
  - Расстояние деспавна 200 считается от якоря, а не от границы.
  - Добавлены: min_spawn_distance, потолок роста задержки, повтор попытки при
    достигнутом лимите, пауза спавна после захвата, правило starved.

================================================================================
12. СМЕНА ТЕРРИТОРИИ (БИОМЫ И БЛОКИ)
================================================================================
12.1. Идея
Файлы мира (карта войны) всегда содержат ВРАЖЕСКИЙ вид сектора (ENEMY).
При захвате часть блоков и биом заменяются на «игроковые»; при потере —
возвращаются. Мир войны СТАТИЧЕН (randomtickspeed 0, игроки не строят и не
ломают), ЕДИНСТВЕННОЕ ИСКЛЮЧЕНИЕ — форпосты (раздел 13).

12.2. Правила замены (sectors.<id>.replaces)
  biome: "ВРАЖЕСКИЙ,ИГРОКОВ" — на захвате ВСЕ биомные ячейки сектора
         становятся биомом игроков; при потере — биомом врагов. (Не «только
         где был биом X» — весь сектор.)
  blocks: rule_N: "БЛОК_ВРАГОВ,БЛОК_ИГРОКОВ" — каждый блок материала врагов
         в секторе (во всей высоте) заменяется на блок игроков и обратно.
  Валидация: материалы существуют, исходный ≠ целевой, ОБА имеют одинаковый
  набор свойств состояния (BlockData), т.к. замена переносит свойства через
  BlockData#merge. Нельзя использовать блоки с тайл-сущностями (сундуки,
  таблички, спавнеры…). При нарушении — правило отбрасывается с WARNING.
  Если у двух правил совпадает исходный материал — ошибка.

12.3. Журнал замен (бинарный файл на сервер)  [ОБЯЗАТЕЛЬНО]
  Путь: data/transforms/<sector_id>.bin. Формат (версия 1):
   - magic "IFJ1", u16 версия;
   - заголовок: UTF-8 JSON c длиной: sector_id, world, coords_hash,
     replaces_hash, правила (материалы), биомы, дата создания;
   - u32 число чанков; индекс: по каждому чанку (cx, cz, offset, length);
   - данные чанка: список правил: (u16 rule_index, varint count, позиции).
     Позиция упакована: (y−minY) 9 бит + (z&15) 4 бита + (x&15) 4 бита; в
     пределах правила — отсортированы и закодированы дельтами (varint);
   - CRC32 в конце.
  Журнал создаётся СКАНИРОВАНИЕМ: для каждого чанка сектора асинхронно
  загрузить (getChunkAtAsync), взять ChunkSnapshot, асинхронно пройти по
  столбцам, входящим в сектор (маска), по всей высоте; сопоставить Material с
  материалами «врагов»; записать позиции. Параллелизм — transform.scan_threads.
  Это ТЯЖЁЛАЯ операция уровня разработки: на живом сервере не запускать
  (выполняется при старте после изменения конфигов или по /if sectors rescan,
  12.8). Индекс журнала держать в памяти, данные чанков читать по требованию
  (async), небольшой LRU-кэш (~64 чанка).
  Почему файлы, а не MySQL: многомегабайтные BLOB замедляют БД и репликацию;
  мир на каждом сервере свой, и журнал строится детерминированно из него же.

12.4. Маркеры прогресса в чанках  [ОБЯЗАТЕЛЬНО]
  В PersistentDataContainer КАЖДОГО затронутого чанка хранится ключ
  ironfrontiers:tf_<sector_id в нижнем регистре> = целое k (0..N): «первые k
  записей журнала (в порядке применения) уже в ИГРОКОВОМ виде». k=0 — враждебный
  вид, k=N — полностью игроковый. И ключ ...:bio_<id> = 0/1 (биом).
  Желаемое состояние сектора задаёт цель: PLAYER → увеличивать k до N;
  ENEMY → уменьшать k до 0 (откат идёт в обратном порядке). Это делает смену
  ПРЕРЫВАЕМОЙ в любой момент и устойчивой к падению сервера: маркер обновляется
  в тот же тик, что и блоки, и хранится вместе с чанком.
  Порядок записей фиксирован: сортировка по направлению (transform_direction
  сектора ?? transform.direction): MIN_X_TO_MAX_X — по x по возрастанию и т.д.
  Порядок записей между чанками — по возрастанию соответствующей координаты
  чанка; внутри чанка записи сортируются при первой загрузке (по ключу
  направления, затем по остальным осям).
12.5. Применение (бюджет и темп)  [ОБЯЗАТЕЛЬНО]
  - Для одной записи: если текущий блок = «исходный» материал правила — установить
    «целевой» (setType-аналог без физики/обновления соседей: Block#setBlockData
    (data, false)), свойства перенести через merge; иначе пропустить (guard).
    Guard делает операцию безопасной на перекрытиях с форпостом (раздел 13.9).
  - Бюджет: за тик тратить не более transform.tick_budget_ms (по System.nanoTime
    между порциями); при TPS ниже transform.min_tps — пауза.
  - Темп: сначала смена БИОМА по чанкам (за biome_change_seconds, чанки по
    возрастанию ключа направления), затем БЛОКОВ — за blocks_change_seconds:
    целевое число обработанных записей к моменту t = N_загруженных ×
    (t − t0)/blocks_change_seconds. Если не успеваем — обрабатываем максимум
    по бюджету (отставание допустимо), если опережаем — ждём. Получается
    «фронт», идущий по сектору в выбранном направлении. Менять биом полностью до
    начала блоков — ОБЯЗАТЕЛЬНО.
  - Незагруженные в момент смены чанки: помечаются «ожидают»; обрабатываются
    ЛЕНИВО при ChunkLoadEvent (приоритетно, но тоже по бюджету), игнорируя темп.
12.6. Биомы
  Ячейка биома — 4×4×4 блока. Для каждого чанка сектора перебрать ячейки по
  всей высоте мира (minHeight…maxHeight шагом 4). Ячейка меняется, если
  в неё попадает ≥ 8 из 16 столбцов, лежащих в секторе (правило большинства);
  у очень маленьких секторов (<8 клеток) биом не меняется (WARNING при
  загрузке). Установка: World#setBiome(x,y,z,biome) для центра ячейки.
  После смены чанк нужно ПЕРЕОТПРАВИТЬ клиентам. [ПРОВЕРИТЬ/СПАЙК] Для
  Paper/Purpur 1.20.6: проверить World#refreshChunk (помечен как нежелательный)
  и, при проблемах, отправку пакета обновления биомов (ClientboundChunks
  BiomesPacket) — интерфейс BiomeRefresher с первой реализацией и запасной.
  Результат спайка — в docs/decisions/. Эффект должен быть виден игрокам
  рядом без перезахода.
12.7. Замена блоков и клиент
  Блоки ставятся без физики, но с обычной рассылкой изменений клиентам. Выпадения
  предметов не допускать (замена, а не разрушение). Игроков и мобов внутри
  блоков не обрабатывать (редкий случай, достаточно ничего не ломать).
12.8. Сверка при старте и «Сброс сектора»  [ОБЯЗАТЕЛЬНО]
  При старте плагина для каждого сектора сравнить хеши: coords_hash,
  replaces_hash и хеш настроек форпоста (blueprint/center/npc/npc_coord) с
  data/sector_meta.json.
   - Совпали → обычная сверка: желаемое состояние из БД ↔ маркеры чанков
     (применяется лениво/по бюджету, 5.3).
   - Не совпали (админ поменял контур, замены, чертёж) → ПРОЦЕДУРА «СБРОС
     СЕКТОРА» (сектор помечен initializing, не участвует в игре):
       1) если часть чанков не в базовом виде — откатить по СТАРОМУ журналу
          (его заголовок хранит старые правила); чанки грузить async;
       2) если физически есть форпост (локальный файл, 13.7) — убрать его по
          журналу перезаписанных блоков (мгновенно, без анимации);
       3) вернуть NPC на парковку;
       4) в БД: состояние ENEMY, occupation_left=0, форпост NOT_BUILT,
          прогресс пожертвований сбросить (пожертвования не возвращаются);
       5) удалить старый журнал, просканировать новую базу, записать журнал и
          sector_meta.json.
   - Сектор есть в журналах/БД, но удалён из sectors.yml («сирота»): выполнить
     откат по журналу и удалить его файлы/строки (аналог delete).
   - Для правок карты внутри сектора (админ подправил блоки): команда
     /if sectors rescan <имя> (только при состоянии ENEMY и форпосте
     NOT_BUILT, и когда все маркеры = 0). Пересоздаёт журнал.
   Требуется РЕСТАРТ для изменений, перечисленных в 6.2.1; логируйте на
   старте: «Сектор X: обнаружены изменения, выполняется сброс…» и итог.
12.9. Взаимодействие с форпостами — см. 13.9 (guard + нормализация).
12.10. Многосерверность: каждый сервер хранит свой журнал и маркеры чанков и
  сам приводит свой мир к желаемому состоянию из общей БД (раздел 20).

================================================================================
13. ФОРПОСТЫ (STRONGHOLDS) И ЧЕРТЕЖИ (BLUEPRINTS)
================================================================================
13.1. Идея
Захваченный сектор (SAFE/HELD) можно «укрепить»: игроки сообща сдают ресурсы,
после чего по чертежу строится здание — форпост. Форпост даёт бонусы (13.4).
Форпост ОПЦИОНАЛЕН: секция stronghold в секторе может отсутствовать.

13.2. Состояния форпоста (публичные, для плейсхолдера и БД)  [ОБЯЗАТЕЛЬНО]
  NOT_BUILT — не построен (идёт или не идёт сбор ресурсов).
  BUILDING  — идёт послойная постройка.
  ACTIVE    — построен и исправен (бонусы действуют).
  BROKEN    — разрушен/повреждён после потери сектора (бонусов нет), ждёт ремонта.
  REPAIRING — идёт послойный ремонт.
Допустимые переходы: NOT_BUILT→BUILDING→ACTIVE; ACTIVE→BROKEN (потеря сектора);
BROKEN→REPAIRING→ACTIVE; любое состояние →NOT_BUILT (команда delete или сброс
сектора). Если у чертежа нет link — при потере сектора блоки не меняются, но
состояние всё равно BROKEN (бонусы пропадают), починка = оплата + перерасстановка
(идемпотентная).

13.3. Условия
  - Сбор ресурсов и постройка возможны только в SAFE или HELD. В DESTRUCTION
    и ENEMY — нельзя (меню показывает «заблокировано»).
  - Починка — когда сектор снова у игроков (SAFE/HELD) и форпост BROKEN.
  - Сектор в SAFE с infinite_safe — постройка допустима.

13.4. Награда по умолчанию (админ вправе задавать свою — этап «будущее»; сейчас
реализуется только список ниже, но код Perks должен быть расширяемым)
  - destruction_time × stronghold.destruction_time_multiplier (5,0);
  - safe_time × stronghold.safe_time_multiplier (2,0);
  - kpm_held × stronghold.kpm_held_multiplier (0,9; т.е. −10%).
  Действуют ТОЛЬКО при состоянии форпоста ACTIVE. Одноразовая добавка: если
  форпост ПОСТРОЕН (стал ACTIVE) в состоянии SAFE, к текущему остатку SAFE
  прибавляется (safe_multiplier − 1) × базовый safe_time сектора (при множителе
  2.0 и базе 1 ч → +1 ч; пример: остаток 10 мин → стало 1 ч 10 мин). То же
  правило для ремонта в SAFE. Если построен/отремонтирован в HELD —
  мгновенной добавки нет, множители действуют на будущие SAFE/DESTRUCTION.
  В DESTRUCTION строить нельзя (поэтому продления там нет).
  Не терять расширяемость: класс Perks — реестр «эффектов форпоста»; к нему
  позже заказчик добавит новые.

13.5. Чертёж (blueprints.yml): формат и правила
  - Внутренняя система координат: (0,0,0) — внутренний блок, который
    ставится в center (мировые координаты из sectors.yml). Блок «1,0,0» —
    на +x от центра, «0,0,1» — на +z, «0,1,0» — выше на 1. Отрицательные
    значения допустимы (ниже/левее центра).
  - Ключ — строка "x,y,z" в кавычках. Значение — строка блока в формате
    Bukkit BlockData: "oak_wood[axis=y]", "stone_bricks", "oak_stairs[
    facing=north,half=bottom]". Разбор: Bukkit.createBlockData(String).
    Поддерживаются ТОЛЬКО ванильные блоки.
  - Допустимы только блоки с КОЛЛИЗИЕЙ (material.isCollidable()) и без
    тайл-сущностей (сундуки, таблички, баннеры, спавнеры, головы и т.п.), иначе
    запись невалидна. В broken_strongholds дополнительно допускается AIR.
    Любые сущности (рамки, картины, стойки) ЗАПРЕЩЕНЫ.
  - link (ОПЦИОНАЛЕН, внутри КАЖДОГО чертежа) — имя записи из
    broken_strongholds. Нет link → при потере сектора блоки не меняются.
  - Сломанный чертёж (broken_strongholds.<имя>): те же внутренние
    координаты. При потере сектора заменяются ТОЛЬКО перечисленные позиции;
    остальные блоки постройки ОСТАЮТСЯ. AIR = блок разрушается ЭФФЕКТОМ.
  - Валидация при загрузке: пустой чертёж, неизвестный link, неизвестный
    blueprint в sectors.yml — ошибка; размер чертежа ограничьте разумно
    (предупреждение > 20 000 блоков).

13.6. Жизненный цикл и NPC
  - Для каждого сектора с форпостом в Citizens заранее создан статичный NPC
    (id указан в stronghold.npc). Пока сектор в ENEMY — NPC стоит на
    ПАРКОВКЕ (stronghold.npc_parking) и недоступен игрокам. При захвате (и при
    восстановлении на старте для SAFE/HELD/DESTRUCTION) NPC телепортируется в
    stronghold.npc_coord; при потере — обратно на парковку.
  - Взаимодействие через BetonQuest: диалог NPC вызывает консольные команды
    /if menu open 1 <sector_id> <игрок> (информационное меню) и т.д. Код
    BetonQuest не нужен (18.6).
  - Если NPC с указанным id не найден в Citizens — WARNING при старте,
    форпост этого сектора отключается (меню не открывается).

13.7. Постройка и «перезаписанные блоки»  [ОБЯЗАТЕЛЬНО]
  Автоматика: как только ВСЕ требования собраны (14.5) — постройка стартует
  САМА (состояние BUILDING). Команда /if stronghold build <имя> обходит стоимость
  (раздел 15) и тоже запускает постройку.
  Процедура (идемпотентная, продолжаемая после падения):
   1. Состояние в БД: BUILDING. Локальный файл data/strongholds/<sector>.json
      (атомарная запись: tmp → move): {phase, layer_cursor, blueprint_hash}.
   2. Позиции = center + внутренняя координата; слои — по внутреннему y
      по возрастанию (включая отрицательные); внутри слоя — порядок x,z.
   3. ЧАНКИ под постройкой на время работ держать «билетом» плагина
      (Chunk#addPluginChunkTicket) и снять по окончании.
   4. Перед установкой каждого слоя записать в журнал перезаписанных блоков
      data/strongholds/<sector>.overwritten.bin текущие блоки позиций слоя,
      ЕСЛИ позиции там ещё нет. Записывается НОРМАЛИЗОВАННЫЙ БАЗОВЫЙ вид (13.9).
   5. Слои ставятся с задержкой stronghold.build_layer_delay_ticks (10). Если
      в слое больше stronghold.max_blocks_per_tick блоков — разбить на тики.
      Блоки без физики.
   6. По завершении — состояние ACTIVE (в БД), перк safe (13.4), событие,
      сообщение.
  Постройка идёт на КАЖДОМ сервере (при многосерверности) локально (раздел 20).

13.8. Конвертер «выделение WorldEdit → чертёж»  [ОБЯЗАТЕЛЬНО; заказчик очень
просил]
  Команды (permission ironfrontiers.admin; нужен WorldEdit/FAWE):
   /if blueprint export <имя> [include_air]
   /if blueprint export_broken <имя> [include_air]
  Алгоритм:
   1. Взять выделение админа из WorldEdit (SessionManager→LocalSession→
      getSelection(world)). Нет выделения — ошибка.
   2. Начало координат (0,0,0) = БЛОК, НА КОТОРЫЙ СМОТРИТ админ (raycast ≤ 20
      блоков; getTargetBlockExact). Это будущий center. Нет блока — ошибка.
   3. Размер выделения ≤ blueprint_export.max_blocks (50000), иначе ошибка.
   4. Для каждого блока региона записать «x,y,z» (относительно начала) →
      BlockData#getAsString() без префикса «minecraft:». Воздух пропускать
      (если не указан include_air). Блоки без коллизии и с тайл-сущностями
      пропускать и вывести админу счётчик пропущенных.
   5. Записать в plugins/IronFrontiers/blueprints/<имя>.yml: export пишет секцию
      blueprints.<имя>.blocks, export_broken — broken_strongholds.<имя>. Файл
      с таким именем уже есть → обновить только соответствующую секцию
      (прочитать YamlConfiguration, заменить, сохранить; файл генерируется
      машиной, комментарии админа в нём не ожидаются, но шапка-инструкция
      пишется ВСЕГДА).
   6. Конфликт имён между blueprints.yml и blueprints/*.yml — ошибка при загрузке.
   7. Сообщение: сколько блоков записано, куда, и напоминание про link.
  Шапка-инструкция в генерируемых файлах и в blueprints.yml (на русском):
   «Как пользоваться: 1) выделите постройку WorldEdit (//pos1, //pos2);
    2) встаньте так, чтобы смотреть на блок, который станет центром здания
    (внутренний (0,0,0)); 3) выполните /if blueprint export <имя>; 4) при
    желании создайте «сломанный» вариант (разрушьте часть здания, снова
    выделите, /if blueprint export_broken <имя2>) и в чертеже укажите link:
    <имя2>; 5) в sectors.yml укажите blueprint: <имя> и center: x,y,z
    (мировые координаты блока, на который вы смотрели); 6) /if reload.»

13.9. Совместимость с заменой блоков сектора (раздел 12)  [ОБЯЗАТЕЛЬНО]
  Форпост ставится ПОВЕРХ территории сектора, которая могла быть
  трансформирована. Чтобы не было ошибок при откате:
   - «Guard»: трансформация заменяет блок только если текущий блок = исходный
     материал правила (12.5). Блоки форпоста поверх позиций журнала просто
     пропускаются.
   - «Нормализация к базовому виду»: журнал перезаписанных блоков хранит
     ВРАЖЕСКИЙ (базовый) вид: если на позиции сейчас блок «игроков» из правила
     и позиция есть в журнале замен — записывается блок «врагов». При
     восстановлении (delete/сброс) ставится базовый блок, и если сектор сейчас
     в игроковом виде и позиция в журнале замен — применяется замена в
     «игроковый» (обычная сверка маркеров это обеспечивает: после
     восстановления выполнить reconcile сектора для затронутых чанков).
13.10. Потеря сектора и разрушение (BROKEN)
  При потере сектора, если форпост не NOT_BUILT: состояние BROKEN (БД), затем
  анимация разрушения (только на тех позициях, что перечислены в broken):
   - группировка по внутреннему y, слои СВЕРХУ ВНИЗ с задержкой
     stronghold.break_layer_delay_ticks;
   - если целевой блок AIR — «разрушение с эффектом»: на позиции
     world.spawnParticle(Particle.BLOCK, центр, 20, 0.3, 0.3, 0.3, blockData) и
     звук разрушения блока (block.getBlockData().getSoundGroup().getBreakSound());
     частицы определяются разрушаемым блоком;
   - иначе блок просто заменяется на broken-вариант (без выпадения предметов);
   - перезаписываемые позиции, которых нет в журнале перезаписанных блоков
     (позиции только из broken) — предварительно записать (13.7 п.4).
  Обязательный параметр: в течение occupation_time (10.4) сектор нельзя
  отвоевать — этого времени должно хватать на анимацию. При загрузке конфигов
  проверять: occupation_time ≥ (слои×задержка) + transform.* и предупреждать.
13.11. Ремонт
  Меню (14) для состояния BROKEN показывает вместо «Построить» — «Починить» и
  требования requirements_repair. Все требования собраны → автоматически
  REPAIRING: идемпотентная перерасстановка ВСЕХ блоков чертежа (даже тех, что
  не менялись) послойно снизу вверх; потом ACTIVE (+perk safe в SAFE).
  /if stronghold repair <имя> — обход стоимости.
13.12. Удаление (/if stronghold delete <имя>)
  Состояние → NOT_BUILT; блоки форпоста (чертёж + broken-позиции) восстанавливаются
  по журналу перезаписанных блоков (13.9), сверху вниз с анимацией
  (delete_animation: true; иначе мгновенно); журнал перезаписанных удаляется;
  локальный файл состояния удаляется; прогресс пожертвований обнуляется БЕЗ
  возврата. Бонусы исчезают немедленно. NPC остаётся (сектор у игроков).
  Пожертвования НЕ возвращаются никогда: ни при потере сектора, ни при delete,
  ни при сбросе, ни при командах build/repair (накопленное просто забывается).

14. МЕНЮ ФОРПОСТА И ПОЖЕРТВОВАНИЯ
================================================================================
14.1. Два меню (открываются командами /if menu open 1|2 <sector_id> <игрок>)
МЕНЮ 1 (9 слотов, информационное):
  - слот описания: лор-описание лагеря + список улучшений (текст из menus.yml);
  - слот «Стоимость» (ЛКМ → открывает меню 2): в lore список требований с
    прогресс-барами; для состояния BROKEN — «Починить» и requirements_repair;
  - последний слот — «Закрыть». Остальные — заполнитель.
МЕНЮ 2 (27 слотов, пожертвования):
  - интерактивные слоты (количество и расположение настраиваются) — игрок кладёт
    туда предметы: перетаскиванием, обычным кликом или Shift+ЛКМ из своего
    инвентаря;
  - слот-подсказка: дублирует стоимость и прогресс (те же строки);
  - слот «Закрыть»; слот «Назад» (в меню 1); кнопка «Пожертвовать» (по
    умолчанию ПОСЛЕДНИЙ слот, индекс 26).
Умолчания раскладки: интерактивные 0–4 и 9–13; подсказка 6; закрыть 8;
назад 17; кнопка 26; остальное — заполнитель.

14.2. Проверки при открытии
  Команда проверяет: сектор есть и у него есть stronghold; сектор в SAFE/HELD
  (для меню 2 — также форпост NOT_BUILT/BROKEN); игрок онлайн. Иначе —
  сообщение из messages.yml. (Даже если команду вызвал BetonQuest от консоли —
  проверки обязательны.)
14.3. Что считается требованием  [ОБЯЗАТЕЛЬНО]
  requirements.<ключ>: {type: VANILLA|MMOITEMS|ITEMSADDER, id, count,
  display_name (опц.)}. Сопоставление предмета с требованием — ItemMatcher:
   - VANILLA: только ЧИСТЫЕ предметы: материал совпал И нет ItemMeta-
     «украшений» (имени, lore, CustomModelData, чар, PDC-ключей любых
     плагинов, повреждений сверх нуля). Иначе MMOItems/ItemsAdder-предметы на
     ванильной основе засчитались бы как обычные.
   - MMOITEMS: id формата ТИП:ID (например MATERIAL:IRON_BAR) — через API
     MMOItems (18.4).
   - ITEMSADDER: namespace:id — через CustomStack (18.5).
   Реестр ItemMatcherRegistry (расширяется новыми типами).
14.4. Правило пожертвования  [ОБЯЗАТЕЛЬНО]
  Нажатие на кнопку «Пожертвовать»:
   1. Просмотреть предметы в интерактивных слотах и для каждого найти
      подходящее требование.
   2. Если ЕСТЬ предмет, который (а) не подходит ни к одному требованию ИЛИ
      (б) относится к требованию, по которому уже всё сдано (остаток 0), —
      кнопка ЗАБЛОКИРОВАНА (состояние blocked: красный материал/lore «уберите
      лишние предметы»), клик ничего не делает, пишется подсказка.
   3. Иначе для каждого требования R: offered(R) = сумма предметов в слотах;
      accepted(R) = min(offered, остаток(R)); излишек (offered−accepted)
      ВОЗВРАЩАЕТСЯ игроку (в инвентарь; не влезло — выбросить у ног).
   4. accepted списываются из слотов; в БД атомарно увеличивается прогресс;
      обновляются статистика игрока (суммарно предметов, число нажатий
      «пожертвовать» +1 за успешное нажатие) и событие DonationEvent.
   5. Если ВСЕ требования выполнены — постройка/ремонт стартует автоматически.
  Примеры (стоимость: камень 20, земля 10, обсидиан 64):
   - Игрок №1 кладёт 15 камня → принято 15 (камень 15/20).
   - Игрок №2 кладёт 10 камня и 32 обсидиана → принято 5 камня и 32
     обсидиана, 5 камня возвращено.
   - Игрок №3 кладёт 10 земли, 5 камня, 1 кирпич → кнопка заблокирована
     (камень уже 20/20 и кирпич не нужен); уберёт камень и кирпич — сможет
     сдать землю.
  Конкурентность: все операции — на главном потоке; решение по остатку
  принимается в момент клика; запись в БД — атомарным UPDATE (в многосерверном
  режиме остаток берётся из БД транзакцией, 20.7).
14.5. Прогресс-бар  [ОБЯЗАТЕЛЬНО]
  Формат строки требования (настраивается): «{display}: {done}/{count} {bar}
  {percent}%». Бар: 20 делений символа ⏽ (настраиваемый символ), 1 деление =
  5%; число заполненных = floor(done×20/count); заполненные — цвет &a, пустые
  — &8 (цвета и символ в menus.yml). 100% только при done=count. Пример для 100
  камня при 37 сданных: «37/100 ⏽⏽⏽⏽⏽⏽⏽ (7 зелёных, 13 серых) 37%».
  Символ ⏽ (U+23FD) может не отрисоваться в стандартном шрифте — [ПРОВЕРИТЬ]
  в клиенте с ресурспаком сервера; символ — настраиваемый.
14.6. Постоянное обновление  [ОБЯЗАТЕЛЬНО]
  Пока меню открыто, динамические предметы (стоимость/подсказка/кнопка)
  перерисовываются каждые menus.update_interval_ticks (10; в menus.yml можно
  переопределить для каждого меню). Перерисовывать только изменившиеся
  предметы (сравнение lore). Клиент при смене предмета обновляет tooltip в
  реальном времени. Источник данных — кэш прогресса в памяти (его обновляют
  донаты и, в многосерверном режиме, сообщения кластера).
  Меню не должно позволять «вытащить» предметы заполнителя/кнопок: отменять
  InventoryClickEvent/InventoryDragEvent на неинтерактивных слотах; обработать
  Shift+ЛКМ из инвентаря игрока (вручную переносить только в интерактивные
  слоты); при закрытии меню, выходе игрока и отключении плагина ВСЕ
  предметы из интерактивных слотов возвращаются игроку.
14.7. menus.yml (структура)
  Комментарий в начале со списком плейсхолдеров меню:
   {sector_id} {sector_name} {sector_state} {stronghold_state} {phase}
   (BUILD/REPAIR) {requirements} (многострочный блок всех требований с барами)
   {total_percent} {player_donated} {sector_donated} {time_left} {perk_safe}
   {perk_destruction} {perk_held} {player_name}
  Ключи: bar {char, segments:20, filled_color:'&a', empty_color:'&8'};
  fill_material: BLACK_STAINED_GLASS_PANE (допустим AIR; любой ванильный
  материал); у каждого меню: title, size (9/27), update_interval_ticks
  (опц.), slots: для каждого предмета slot, material, name, lore (с
  плейсхолдерами меню и PlaceholderAPI), состояния. Состояния: для «cost» —
  available/locked/repair; для «donate» — ready/blocked/empty. Интерактивные
  слоты — список индексов interactive_slots. Названия/lore поддерживают
  MiniMessage и «&»-коды.

================================================================================
15. КОМАНДЫ И ПРАВА
================================================================================
Команда: /if (полное /ironfrontiers:if; алиасы ironfrontier, ironfrontiers).
Права: ВСЕ команды требуют ironfrontiers.admin (меню-команды — тоже, т.к. их
вызывает консоль BetonQuest). TAB-complete ОБЯЗАТЕЛЕН для всех подкоманд и
аргументов: имена секторов (из реестра), blueprints, игроки онлайн, capture|held,
1|2 и т.д. Все сообщения — из messages.yml.

  /if reload
      Перезагрузить все конфиги (6.2.1): сообщение «Конфигурации перезагружены»;
      для каждого изменённого параметра из списка перезапуска — «…, но
      {параметр} требует перезапуска сервера».
  /if sectors list
      Список секторов в чат (10 на страницу не обязательно): id, display_name,
      состояние, kpm/порог, игроки внутри, наличие форпоста; строка кликабельна
      (клик → info; метка [tp] → tp).
  /if sectors info <имя>
      Полная информация: мир, площадь, bounding box, число вершин, состояние и
      остаток таймера (или ∞), kpm сейчас, capture/held (эффективные, базовые и
      override, источник), действующие safe/destruction/occupation и их
      источник, число точек спавна, число игроков внутри, форпост (состояние,
      NPC, center, прогресс требований), флаги (infinite_safe).
  /if sectors tp <имя>
      Телепорт админа на «нулевую точку» (первая вершина; y — безопасная
      высота SurfaceResolver; при отсутствии — ошибка).
  /if sectors create <имя>
      Выдать палку выделения (раздел 8). В многосерверном режиме запрещено
      (dev-операция, 20.9).
  /if sectors delete <имя>
      Запросить удаление; требуется подтверждение (см. /if agree). После
      подтверждения: полный откат — замена блоков/биома к враждебному виду,
      удаление форпоста (по журналу, без возврата ресурсов), NPC на парковку,
      удаление журнала, строки БД, блока из sectors.yml (текстово), сессий
      спавна и мобов. Запрещено в многосерверном режиме.
  /if agree   (и слово «agree» в чате)
      Подтверждение последней опасной команды ЭТОГО админа в течение
      confirmations.timeout_seconds; слово в чате перехватывается и не
      отправляется остальным. Без ожидающего запроса — сообщение об ошибке.
  /if sectors show <имя>
      Показать границы частицами на selection.show_duration_seconds секунд.
  /if sectors set <имя> capture|held <значение>
      Override порога (10.10).
  /if sectors rescan <имя>
      Пересканировать мир сектора и пересоздать журнал (12.8). Только при ENEMY,
      форпост NOT_BUILT; запрещено в многосерверном режиме.
  /if stronghold build <имя> | repair <имя> | delete <имя>
      Принудительные действия, обходят стоимость; накопленное забывается;
      delete — с подтверждением /if agree.
  /if menu open 1|2 <имя> <player> ; /if menu close <player>
      Для BetonQuest/консоли. 1 — информационное меню, 2 — пожертвования.
  /if blueprint export <имя> [include_air] ; /if blueprint export_broken <имя>
      Конвертер WorldEdit→чертёж (13.8).
(В этих командах «имя» = sector_id; для blueprint — имя чертежа.)

16. ПЛЕЙСХОЛДЕРЫ (PlaceholderAPI, префикс if)
================================================================================
Требования: расширение PlaceholderExpansion (persist=true); значения берутся
ТОЛЬКО из кэшированных снимков в памяти (потокобезопасно, без обращений к БД
и без блокировок). Числа kpm форматируются по placeholders.kpm_decimals;
если kpm_strip_trailing_zero=true — «45» вместо «45.0». Время — mm:ss (часы
по необходимости: h:mm:ss), для infinite_safe — infinite_time_text.
Имя сектора в плейсхолдерах — sector_id; разбор по суффиксу (_kpm, _state,
_time, _players, _capture, _held), точные совпадения проверять ПЕРВЫМИ; имена
секторов, совпадающие с зарезервированными словами (kpm, sum, name, id, state,
time, players, count, donation), запрещены.

  %if_sector_name%             display_name сектора, где стоит игрок; вне
                               сектора — placeholders.outside_sector_name ('АА00')
  %if_sector_id%               sector_id (вне сектора пусто)
  %if_sector_kpm%              kpm сектора игрока (вне — 0)
  %if_sector_state%            состояние сектора игрока (вне — пусто)
  %if_sector_<имя>_kpm%        kpm сектора
  %if_sector_<имя>_state%      состояние сектора
  %if_player_kpm%              kpm игрока в секторе, где он стоит (вне — 0)
  %if_player_<имя>_kpm%        kpm игрока в указанном секторе
  %if_player_kpm_sum%          суммарный kpm игрока по всем секторам
  %if_player_donation%         всего предметов, сданных игроком за всё время
  %if_donation_sum%            всего предметов, сданных всеми за всё время
  %if_donation_count%          число успешных нажатий «пожертвовать» (всего)
  %if_stronghold_count%        число форпостов в состоянии ACTIVE
  %if_stronghold_state_<имя>%  состояние форпоста сектора (NOT_BUILT…)
Дополнительно (утверждены заказчиком):
  %if_sector_time%             остаток таймера состояния сектора игрока (SAFE/
                               DESTRUCTION; для ENEMY — остаток оккупации)
  %if_sector_<имя>_time%       то же для указанного сектора
  %if_sector_capture%          эффективный порог захвата сектора игрока
  %if_sector_held%             эффективный порог удержания (с бонусом форпоста)
  %if_sector_<имя>_capture% , %if_sector_<имя>_held%
  %if_sector_players%          число игроков внутри сектора игрока
  %if_sector_<имя>_players%    число игроков внутри указанного сектора
  %if_stronghold_progress_<имя>%  общий прогресс сбора/ремонта, % (0–100)
Статистику игроков (donation) и глобальные суммы держать в памяти (загружать
из БД при старте, обновлять при донатах; запись в БД — асинхронно).

17. БАЗА ДАННЫХ (MySQL/MariaDB)
================================================================================
17.1. Принципы
  HikariCP; все обращения — в отдельном пуле (5.4); главный поток БД не ждёт;
  записи копятся и пишутся пачками (write-behind), кроме критичных (смена
  состояния — сразу, но асинхронно). Версия схемы — таблица if_schema +
  последовательные миграции (классы Migration_N). Префикс таблиц —
  database.table_prefix. Кодировка utf8mb4.

17.2. Схема (ориентир; детали типов — решение разработчика)
  if_schema(version INT NOT NULL)
  if_sector_state(
    sector_id VARCHAR(64) PK, state ENUM('ENEMY','SAFE','HELD','DESTRUCTION'),
    state_left_s INT NULL, occupation_left_s INT NOT NULL DEFAULT 0,
    destruction_saved_s INT NULL, resume_window_left_s INT NOT NULL DEFAULT 0,
    version BIGINT NOT NULL DEFAULT 0, leader_epoch BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMP)
  if_sector_override(sector_id VARCHAR(64) PK, kpm_capture_tenths INT NULL,
    kpm_held_tenths INT NULL)
  if_stronghold(sector_id VARCHAR(64) PK,
    state ENUM('NOT_BUILT','BUILDING','ACTIVE','BROKEN','REPAIRING'),
    version BIGINT, leader_epoch BIGINT, updated_at TIMESTAMP)
  if_stronghold_progress(sector_id, phase ENUM('BUILD','REPAIR'),
    requirement_key VARCHAR(64), donated INT, PRIMARY KEY(sector_id, phase,
    requirement_key))
  if_player_stats(uuid CHAR(36) PK, donated_items BIGINT, donation_clicks INT,
    updated_at)
  if_donation_log(id BIGINT AUTO_INCREMENT PK, uuid, sector_id, phase,
    requirement_key, amount INT, server_id VARCHAR(32), created_at) — для аудита
  if_cluster_meta(k VARCHAR(32) PK, v VARCHAR(255)) — leader_epoch,
    last_leader_heartbeat и т.п.
  Первая таблица, которую нужно сделать (этап 2) — if_sector_state.
17.3. Что НЕ хранится в БД: журналы замен (файлы), состояние чанков (PDC),
  локальные состояния строительства (файлы JSON) — они локальны для сервера.
17.4. Отказоустойчивость
  - БД недоступна при старте: плагин НЕ запускает механики секторов
    (состояние неизвестно), пишет SEVERE, команды выдают понятную ошибку.
  - БД пропала во время работы: записи копятся в памяти (ограничение
    размера), попытки повторяются с экспоненциальной паузой, WARNING раз в минуту.
  - Строка сектора есть в конфиге, но нет в БД → создать (ENEMY). Строка в
    БД без сектора в конфиге → «сирота» (12.8).

18.1. PrivateMobsX (ГЛАВНАЯ интеграция; плагин пишет заказчик)
Сейчас в PrivateMobsX API НЕТ. Разработчик Iron Frontiers РАЗРАБАТЫВАЕТ
согласованный API вместе с заказчиком (или пишет заказчику требования и
ждёт). Нужно следующее (оформить как отдельный модуль privatemobsx-api,
сервис через Bukkit ServicesManager, потокобезопасные неизменяемые DTO):

  Интерфейс PrivateMobsApi:
   - SpawnResult spawn(UUID owner, MobSpec spec, Location loc, Map<String,String>
     tags)  — спавн ОДНОГО личного моба для owner. Вызывается на главном потоке.
     SpawnResult: успех (PrivateMobHandle) или причина отказа: INVALID_MOB,
     CHUNK_NOT_LOADED, OWNER_OFFLINE, LIMIT_REACHED, ERROR.
   - MobSpec: type (VANILLA|MYTHICMOBS), mobId (EntityType или id Mythic),
     level (int, nullable; для VANILLA игнорируется).
   - PrivateMobHandle: UUID mobId (entity uuid), UUID owner, tags (read-only),
     boolean isAlive(), Location location().
   - void despawn(PrivateMobHandle h, DespawnReason reason) — удалить без
     события смерти и без дропа (дроп/опыт — только при смерти от игрока).
   - int despawnByTag(UUID owner, String tagKey, String tagValue, reason) —
     удалить всех мобов игрока с тегом (по сектору); возвращает число. Должно
     работать ПО ПОРЦИЯМ, если Iron Frontiers просит (параметр maxPerCall), либо
     просто возвращать список дескрипторов для порционного удаления самим IF.
   - Collection<PrivateMobHandle> getMobs(UUID owner[, tagKey, tagValue]).
   - boolean isPrivateMob(Entity e); Optional<PrivateMobHandle> byEntity(Entity e).
   - int removeAllOrphans() — «подметание» при старте (удалить мобов, не
     привязанных ни к одной активной сессии).

  События (Bukkit, наследники Event, вызываются на главном потоке):
   - PrivateMobSpawnEvent(handle)
   - PrivateMobDeathEvent(handle, UUID owner, @Nullable Player killer, tags)
     ← ключевое для Iron Frontiers: по нему считается kpm и состояние кластера.
   - PrivateMobDespawnEvent(handle, DespawnReason)
  DespawnReason: DEATH, API, OWNER_QUIT, WORLD_CHANGE, UNLOAD, PLUGIN_DISABLE.

  Дополнительные требования к PrivateMobsX:
   - ДЕСПАВН СТАРОЙ ЛОГИКИ УДАЛИТЬ (выход игрока, смена мира, отход): теперь
     этим управляет Iron Frontiers. Заказчик убирает логику деспавна из
     PrivateMobsX. Рекомендуется сохранить минимальную «страховку»: если
     в мире остались мобы владельца, который оффлайн более N минут и
     Iron Frontiers не запущен — вычищать их (настраиваемо).
   - Мобы спавнятся НЕПОСТОЯННЫМИ (setPersistent(false)), чтобы не
     записываться в чанки и не переживать рестарт; при старте IF вызывает
     removeAllOrphans().
   - Теги — произвольные строки; хранить в памяти (Map) и в PDC сущности.
   - Учёт убийцы: если моб убит не владельцем (урон другими, падение) —
     событие всё равно приходит с killer=null/другим; IF сам решает, что считать.
   - Лимиты на владельца и глобальные (счётчики) с кодом отказа LIMIT_REACHED.
   - Уровень для Mythic: параметр level при спавне (int); раскрытие %mmocore_level%
     НЕ делается в PrivateMobsX — IF передаёт готовое число.
   - API не должен вызывать Bukkit-методы с других потоков.
   Нужно ТАКЖЕ: короткий README по PrivateMobsX (как он работает внутри:
   реальные сущности, скрытые пакетами ProtocolLib, или фейковые?), потому что

  Адаптер в IF: PrivateMobsBridge (интерфейс) + реализация PrivateMobsXBridge.
  Для автономной разработки (до готовности API) — FakePrivateMobsBridge

20. МНОГОСЕРВЕРНОСТЬ (реализуется в ЭТАПЕ 6, но закладывается с этапа 1)
================================================================================
20.1. Цель и вкл/выкл
Сервер может вырасти: максимум онлайна одного сервера ограничен, поэтому
планируется до ~10 серверов в одной «связке», подключаемых ПОСТЕПЕННО.
Серверы связаны прокси Velocity (игроки переходят между ними), общей MySQL и
Redis. Задачи: общий захват секторов (суммарный kpm всех серверов), общее
строительство (общий пул ресурсов, форпост строится на всех серверах),
согласованное состояние мира на всех серверах.
  multiserver.enabled — по умолчанию false; смена требует рестарта. При false:
  не создаются Redis-соединения/потоки, классы Jedis не загружаются,
  Authority = AlwaysLeader, лишних процессов нет.
Допущения заказчика: миры и конфиги на серверах ИДЕНТИЧНЫ, плагин это не
проверяет «принципиально» — но см. 20.12 (мягкая диагностика).

20.2. Роли
Нет «главного сервера по конфигу». Все серверы — равноправные кандидаты.
ЛИДЕР (один в каждый момент): пересчитывает автомат состояний, держит
таймеры, пишет состояния секторов/форпостов, решает старт постройки.
Остальные (ФОЛЛОВЕРЫ): считают убийства своих игроков, публикуют kpm, служат
игрокам (меню, спавн), применяют глобальное состояние к СВОЕМУ миру.

20.3. Выбор лидера (lease + epoch)  [ОБЯЗАТЕЛЬНО]
  - Redis-ключ if:leader = "<server_id>|<epoch>" с TTL leader_lease_seconds
    (10). Захват (Lua-скрипт, атомарно): если ключа нет → INCR if:epoch →
    SET if:leader "<id>|<epoch>" PX ttl NX. Продление — каждые
    leader_heartbeat_seconds (3): Lua «если значение моё → PEXPIRE». Не
    удалось продлить → немедленно перестать быть лидером (остановить автомат).
  - Кандидаты пытаются захватить ключ каждый heartbeat, пока лидера нет.
  - epoch — ограждающий токен (fencing): все записи лидера в MySQL содержат
    leader_epoch; обновления вида UPDATE … WHERE leader_epoch <= :epoch, чтобы
    «забытый» старый лидер после разрыва сети не перезаписал новые данные.
  - Пока лидера нет (до lease секунд) автомат стоит — потерь секторов НЕТ,
    followers продолжают считать kpm. Это безопасное вырождение.
  - Новый лидер: читает состояния из MySQL, kpm-окно — из Redis Stream
    (XRANGE за window_seconds+5), таймеры продолжает с сохранённых остатков
    (потеря ≤ state_persist_interval_seconds).
  - Холодный старт: if_cluster_meta.last_leader_heartbeat обновляется лидером;
    если при избрании он старше cold_start_gap_seconds — кластер стартовал
    «холодно» → лидер включает холостой старт (10.6). Обычный failover
    холостой старт НЕ включает.
20.4. Суммирование kpm
  - Каждый сервер раз в kpm.update_interval_seconds публикует в Redis Stream
    if:kpm (XADD … MAXLEN ~ 20000) запись: {server, t (секунда конца
    интервала), sectors: {id: десятые за интервал}} — только ненулевые.
  - Лидер (async-поток, XREAD BLOCK) принимает записи ДРУГИХ серверов и
    добавляет в KpmWindow сектора в бакет секунды t; свои убийства добавляет
    напрямую. KpmSource на лидере = локальное окно (суммарное).
  - Лидер публикует снимок (PUBLISH if:snapshot, JSON): kpm/состояния/остатки
    таймеров по секторам, состояния форпостов, суммарное число игроков кластера.
    Followers обновляют ЛОКАЛЬНЫЕ снимки (для плейсхолдеров и меню).
  - Персональный kpm игрока — только на его сервере.
  - Вариант «считать kpm прямо в MySQL» ОТКЛОНЁН: задержка опроса и нагрузка;
    Redis — правильный инструмент для горячих счётчиков, MySQL — для состояния.
20.5. Состояние и рассылка
  Источник истины — MySQL. После перехода состояния лидер: (1) CAS-запись в
  MySQL (version+1, epoch); (2) PUBLISH if:events {type:STATE_CHANGED, sector,
  version}. Followers по событию читают строку из MySQL (async) и запускают
  reconcile (5.3). Подстраховка от потерянных pub/sub-сообщений: каждые 30 с
  follower сверяет версии всех секторов/форпостов с БД (один дешёвый запрос).
20.6. Подключение нового сервера
  Новый сервер (identical copy) при старте: читает ВСЁ состояние из MySQL
  (секторы, форпосты, прогресс, статистику), запускает reconcile (применение
  блоков/биомов лениво и по бюджету; постройка/разрушение форпостов; NPC),
  подписывается на Redis, шлёт heartbeat. Лидером может стать после
  первичной загрузки состояния (флаг ready). Дополнительных «ручных» шагов нет.
20.7. Форпосты и общий пул ресурсов
  - Прогресс — if_stronghold_progress (общий для всех серверов). Донат: на
    сервере игрока транзакция (SELECT … FOR UPDATE по строкам требований →
    вычислить accepted → UPDATE → COMMIT). Только после успешного COMMIT
    списать предметы и вернуть излишек. Не удалось (БД недоступна) — донат
    отклоняется, предметы не трогаются. После коммита PUBLISH if:events
    {DONATION, sector, phase}: остальные серверы обновляют кэш прогресса (меню
    обновляются).
  - Завершение сбора: сервер, на котором завершён последний взнос, шлёт запрос
    лидеру (20.9); лидер проверяет «все требования выполнены» → CAS
    if_stronghold.state=BUILDING → PUBLISH → ВСЕ серверы строят форпост
    локально и независимо (13.7). Лидер переводит в ACTIVE, когда завершил свою
    локальную постройку; остальные достраивают по своему темпу. Аналогично
    BROKEN (потеря сектора) и REPAIRING, NOT_BUILT.
20.8. NPC
  Расположение NPC выводится из глобального состояния: сектор не ENEMY → NPC
  в npc_coord, иначе на парковке. Лидер пишет в if_stronghold поле npc_state
  (AT_SECTOR/PARKED) вместе со сменой состояния; все серверы телепортируют
  своих NPC (одинаковые id в Citizens — на доверии заказчика). Если позже
  появятся ручные перемещения — добавить поля координат в ту же запись и
  рассылку (схема расширяема).
20.9. Команды в многосерверном режиме
  - /if sectors create | delete | rescan — ЗАПРЕЩЕНЫ (операции этапа разработки;
    выполняются при выключенной многосерверности на одном сервере, конфиги
    потом раскатываются на остальные).
  - /if sectors set, /if stronghold build|repair|delete — выполняются на любом
    сервере, но решение принимает ЛИДЕР: запрос в Redis Stream if:req
    (correlation id) → лидер проверяет и пишет состояние → ответ в
    if:resp:<server_id> (таймаут 5 с, иначе ошибка админу).
  - /if menu …, /if sectors list|info|tp|show, /if reload — локальные (reload
    админ выполняет на каждом сервере).
20.10. Отказоустойчивость
  Redis недоступен: лидер теряет lease и уходит в follower (автомат стоит);
  followers копят kpm локально (буфер ≤120 с). Потерь секторов нет. MySQL
  недоступна: см. 17.4 (донаты отклоняются). Перезапуск лидера — выбирается
  следующий. Серверное время нужно только для TTL Redis; игровые таймеры — в
  остатках секунд.
20.11. Redis-ключи (префикс if:)
  leader (STRING, TTL), epoch (INT), kpm (STREAM), req (STREAM), resp:<id>
  (LIST/STREAM), servers (HASH: id → heartbeat JSON {ts, players_online,
  config_hash, plugin_version}), каналы pub/sub: events, snapshot.
20.12. Мягкая диагностика идентичности
  heartbeat содержит config_hash (хеш sectors.yml + mobs.yml + blueprints* +
  menus.yml) и версию плагина. Лидер при расхождении пишет WARNING и
  (опционально) сообщение игрокам с правом ironfrontiers.admin. Блокировать
  работу НЕЛЬЗЯ (на доверии).
20.13. Что закладывается до этапа 6  [ОБЯЗАТЕЛЬНО]
  Интерфейсы 5.2; поля version и leader_epoch в БД; принцип reconcile (5.3);
  бакеты kpm в десятых; никаких веток «if (одиночный режим)» в ядре — только
  реализации интерфейсов; состояние npc_state в БД с этапа 5.
